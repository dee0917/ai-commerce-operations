# 已知地雷（PITFALLS）

這份文件記錄這條產線在實際量產電商站的過程中，**真的踩過而且會重複發生**的問題。

流程、設計規範、品質標準寫在 `SKILL.md` 與 `references/`，那些告訴你「應該怎麼做」。
這份文件補的是另一半：**照著做也還是會出事的地方在哪裡，怎麼提早發現，發生了怎麼修**。

每一條都來自實際發生過的狀況，不是預想的風險。第一次接手這條產線的人，建議先整份看過一次，
再開始建站；出狀況時用標題回頭查。

**名詞說明（第一次出現）**

| 名詞 | 意思 |
|---|---|
| SPA | Single Page Application，單頁應用。整站只有一個 HTML 檔，頁面切換由瀏覽器端的程式碼負責，不是每頁跟伺服器要一份新的 HTML |
| 熱連（hotlink） | 網頁上的圖片直接指向別人網站的網址，圖片檔案不在自己的專案裡 |
| persist | 把購物車之類的狀態寫進瀏覽器本機儲存空間，讓使用者重新整理頁面後資料還在 |
| stale build | 過期的建置產物。原始碼改了，但部署上去的還是上一次建置出來的舊檔案 |
| 別名（alias） | 對外的固定網址。每次部署會產生一個新的臨時網址，別名要另外指過去才會生效 |
| 假陰性 | 檢查工具回報「沒問題」，但實際上有問題，只是工具抓不到 |

## 一、生成階段

### 每個站的外觀都不一樣，但骨架完全一樣

**症狀**：單看一個站沒問題，把五個站排在一起看就露餡。配色、字體、圖片全都不同，
但首頁區塊順序一模一樣（首屏、精選商品、分類、評價、電子報、頁尾），分頁組合也一模一樣。
有經驗的人一眼看得出是同一套邏輯生出來的。

**原因**：視覺變化做在「表面層」（配色、字體、框架選擇），沒做在「結構層」。
版型模板挑了幾十種，但區塊的出場順序與頁面清單是寫死的，等於一個模板套 N 次。

**做法**：結構本身要隨機化，見 `references/structural-variation.md`。
三件事都要變：①首頁哪些區塊出現、以什麼順序出現 ②站有哪些分頁 ③同一種區塊用哪種排法。
分頁組合要跟著商品品類走（服飾配尺寸指南、食品配成分與訂閱、3C 配規格與相容性），
核心頁（首頁、商品列表、商品內頁、購物車、結帳）則永遠都在。
生完兩個站要實際對照過結構真的不同，不要只看截圖覺得「長得不一樣」就算過。

### 防重複的回寫時機晚於讀取時機，平行執行時會靜默失效

**症狀**：`data/design-history.json` 的防重複規則寫得好好的，也有人照著讀，
但兩個站並排一看還是同一種底色配同一類標題字。查歷史檔會發現規則沒有被違反，
因為做第二個站的時候，第一個站根本還沒被寫進去。

**原因**：**讀取在「選設計基因」的時候，回寫在「站做完」的時候。**
中間隔著整個建站流程，短則幾十分鐘。兩個站平行建置時，後開工的那支讀到的是舊資料，
防重複檢查照樣全過，然後兩個站選到同一組。這種失效不會報錯、不會留下痕跡，
只有把成品並排看才發現得了。

2026-08-04 實測：站二鎖定設計基因的時間比站一完工**早 188 秒**，
兩個站都選了暖紙底＋襯線大標。同一個檔案另外還有一種失效方式：
連續 4 個站根本沒人回寫，防重複檢查形同虛設。

**做法**：把回寫改成**訂位**，選中的當下就登記，不要等站做完
（像訂位，選中就登記，不用等入座）。

1. 選定 DNA、底色、字體的那一刻跑 `scripts/design_history.py reserve`，
   狀態記成 `in_progress`；交付後 `commit`，做不下去 `abandon`。
2. **檢查與登記必須在同一把檔案鎖裡完成。** 分成「先檢查、再寫入」兩個動作的話，
   兩支流程還是可能在中間那個空檔同時通過檢查。
3. 未完工的訂位一樣會擋人，這正是重點；但 `in_progress` 超過 120 分鐘沒下文會自動失效，
   免得中途當掉的站永久佔著一組基因。
4. 寫檔一律先寫暫存檔再 `os.replace`，不要用 `w` 模式直接開原檔。

**一般化**：任何「先讀共用狀態、後寫共用狀態」的防重複機制都有這個問題。
判斷方式很簡單：**如果兩支流程同時跑，後面那支讀得到前面那支的決定嗎？**
讀不到就是這個地雷，跟間隔多久無關。

### 文案一看就是機器寫的，或殘留沒翻譯的語言

**症狀**：滿版的空洞形容詞（elevate your spirit、crafted with intention、curated collection），
用破折號把兩個短句黏成一句，「不是 A，而是 B」的句型反覆出現。
更明顯的是整段沒翻到的原始語言直接留在頁面上。

**原因**：生成時沒有把「寫給誰看、用哪個語言、什麼語氣」定死，模型就會退回預設腔調；
多語言站的文案是分批生的，漏掉的段落不會有人報錯。

**做法**：文案規則見 `references/site-quality-rubric.md` 的品牌文案維度。
交付前用瀏覽器實際開頁面掃殘留語言，不要用命令列的正則比對（原因見驗收章節的假零命中那條）。

### 為了做出「成熟電商的樣子」，生出違法的促銷元素

**症狀**：每個商品都有劃線原價與折扣標籤、頁面上有重新整理就歸零的倒數計時、
「Only 3 left」的固定文字、有名有姓的假評論、預設勾選的加購選項。

**原因**：「成熟的電商站長這樣」被寫成了規則，於是這些元素變成每站必生。
問題是這些手法在英國與歐盟受法規管制，劃線原價必須以該商品過去 30 天內的最低售價為基準，
拿不出基準就是不實標價，假評價與預設勾選同樣明文禁止。這不是風格問題，是會吃罰單的問題。

**做法**：完整禁區與法源見 `references/anti-patterns.md` 的 L1 至 L6。
判斷原則是**這些元素不是全面禁止，是有真實依據才可以用**；
拿不出依據時的預設行為是**不生成該元素**，而不是生成一個假的。
沒有價格歷史的新品就不劃線；沒有真實截止時間就不放倒數；示範資料的站一律不得劃線。

### 畫面上沒看到違規元素，不代表資料裡沒有

**症狀**：檢查工具掃過渲染出來的畫面判定乾淨，實際上假特價的欄位早就躺在商品資料檔裡
（`data/products.json`、`src/data/mockData.ts` 這類位置），只是目前的版型還沒把它畫出來。
換一個版型、或未來某次改動接上那個欄位，違規就直接上線。

**原因**：檢查只堵渲染出口，沒堵資料源頭。

**做法**：掃描範圍要涵蓋整個專案，不能只掃元件目錄。
`compareAtPrice`、`salePrice`、`originalPrice` 這類欄位只要帶著值就要攔，即使畫面上沒出現。
實測過的教訓：三個站只掃渲染端是二比三違規，補上資料端掃描是三比三全部違規。

## 二、建置階段

### 白屏：頁面開起來整片空白，主控台不一定有錯

**症狀**：建置成功、部署成功，開站就是一片白。反覆修反覆白。

**原因**：實際發生過的成因有五種，都會產生同一個症狀。
①資料檔沒生出來或路徑不對 ②CSS 的 import 順序錯 ③型別檢查的嚴格模式擋住編譯
④入口檔沒更新，或路由定義與實際元件名稱對不上 ⑤進場動畫在資料載入完成前就執行，
元素的透明度停在 0。

**做法**：白屏不要靠猜。先看主控台有沒有錯誤，沒有錯誤就往第 ④ ⑤ 種去查，那兩種是靜默的。
建置流程本身可用 `scripts/auto_fix_build.py` 先把型別錯誤收斂掉。

### 購物車看起來有做持久化，重新整理就空了

**症狀**：本機儲存空間裡確實有購物車資料，但重新整理後畫面上的購物車是空的。
程式碼裡也確實掛了 persist，所以稽核時會被判成「有做，沒問題」。

**原因**：購物車狀態裡放了 JavaScript 的 getter（例如 `get subtotal()`）。
getter 不會被序列化成 JSON，狀態還原時整份合併會壞掉。
這比單純沒做持久化更隱蔽，因為靜態檢查看得到 persist 字樣。

**做法**：只持久化純資料（商品陣列），小計之類的衍生值改在元件裡即時算。
驗收一律用真實操作驗：**加入商品，重新整理，看還在不在**。
不可以用「程式碼裡有沒有 persist」當判準。

### 換頁後停在上一頁的捲動位置

**症狀**：從商品列表滑到一半點進商品內頁，新頁面開在中間，看起來像破版。

**原因**：SPA 換頁不會重置捲動位置，要自己掛。

**做法**：路由層掛上換頁回頂的處理。單頁捲動式的站不適用這條，不要硬套。

### Windows 上找不到 npm

**症狀**：腳本在其他作業系統跑得好好的，在 Windows 上直接報找不到指令，整條流程停住。

**原因**：Windows 上的 npm 實體是 `npm.cmd`，直接以 `npm` 呼叫子行程解析不到。

**做法**：用 `shutil.which("npm") or shutil.which("npm.cmd")` 解析出實際路徑再呼叫。
產線腳本已經修過四處，新寫的腳本要沿用同樣寫法，見 `scripts/preflight_check.py`。

### 批次改商品資料的正則越界，把資料串在一起

**症狀**：批次把圖片路徑寫回商品資料檔之後，第八個商品用的是第七個商品的圖。

**原因**：正則用固定距離（例如 `{0,1200}`）當比對範圍，超出單一商品的邊界，接到下一筆去了。

**做法**：用負向預看鎖住邊界（`(?:(?!slug:)[\s\S])*?` 這種寫法），不要用距離估算。
改完抽驗最後幾筆，越界的錯誤通常出現在後段。

## 三、資料與圖片

### 熱連外部圖床，圖會消失

**症狀**：站剛做好時圖都在，過一段時間回來看是一片破圖，或是某些網路環境下整批圖載不出來。

**原因**：圖片指向外部服務的網址，對方可能改連結、可能擋跨站請求、可能限流。
自己專案裡根本沒有那張圖。

**做法**：所有圖片一律**下載成本機檔案放進專案**再引用。
外部服務只能拿來取得圖檔，不可以留在頁面的 `src` 裡。

### 圖載得動，但跟商品不對版

**症狀**：檢查工具回報破圖數為零，實際打開商品列表，收納盒配的是浴室照片、
頌缽配的是啞鈴照片、風水商品配的是網路線照片。

**原因**：自動檢查驗的是「圖片載入成功」，那是技術問題；
「圖跟商品是不是同一個東西」是語意問題，工具不會知道。

**做法**：**檢查通過不等於對版**。要把商品列表整頁的圖排成一張對照圖，用人眼看過一輪才算過。
這種錯比破圖更傷，破圖看起來像壞掉，放錯圖看起來像亂做。
另外，圖的風格要跟**該站的整體設計調性**走，不是跟商品類別走，
否則同類商品的幾個站會共用同一套圖，一比對就露餡。

### 平行跑太多生圖任務，會安靜地不生圖

**症狀**：一次派出多個生圖任務，回報全部完成，結果部署上去的圖有好幾個站是離題的或是舊的。

**原因**：生圖服務有併發與額度限制。平行任務互相搶額度，搶不到的那些不會報錯，
會直接跳過生圖繼續往下走，然後回報「完成」。

**做法**：生圖任務**序列化，一次最多一到兩個**。非生圖的工作可以照常平行。
生圖失敗就標記待補、不要原地重試迴圈，避免卡死。
收到「已完成」的回報不要直接採信，自己去看產出的圖檔。

### 捲動才顯圖的站，靜態截圖會誤判成空白

**症狀**：截圖驗收時看到大片空白區塊，以為圖沒出來，實際上人工開站是正常的。

**原因**：站用了進入視窗才載入或才播動畫的機制，截圖當下那些區塊還沒被觸發。

**做法**：截圖前先把整頁捲到底，再回頭截。不要用第一屏的截圖判斷整頁狀態。

## 四、部署與路徑

### 深層路由直接開會 404

**症狀**：從首頁點進商品列表沒問題，但把商品列表的網址複製到新分頁直接開，
或是在商品內頁按重新整理，出現 404。

**原因**：SPA 只有一個 HTML 進入點，伺服器收到 `/shop` 這種路徑時會去找一個不存在的檔案。
要靠改寫規則把所有路徑都導回入口 HTML。

**做法**：改寫設定檔（例如 `vercel.json`）要放在**專案根目錄**，
只放在 `public/` 底下是不夠的，建置產物目錄也要有一份。
驗收時一定要**直接開深層網址與按重新整理**，只從首頁點進去驗不出這個問題。

### 部署成功了，但對外網址還是舊的

**症狀**：改好、建置好、部署回報成功，打開對外網址還是舊畫面，甚至是 404。
於是開始懷疑是不是建置沒生效，往回改程式碼，改了半天沒用。

**原因**：每次部署產生的是一個新的臨時網址，**對外的固定別名不會自動指過去**。

**做法**：部署完拿到回傳的部署網址後，**明確執行一次別名設定**，然後**去別名網址上驗，不是去部署網址上驗**。
線上沒變的時候，第一個懷疑對象是別名沒更新，不是建置沒生效。這個坑曾經卡住三組人。

### 改了原始碼，部署上去的還是舊建置產物

**症狀**：換了圖或改了元件，重新部署後線上還是舊的，或是出現原本沒有的空白卡片。

**原因**：建置產物目錄殘留上一次的檔案，增量建置沒有覆蓋到。

**做法**：**改過圖片或資源檔就先清掉建置產物目錄，再重新建置**。
空白卡片這個症狀很容易被誤判成程式錯誤，實際上多半只是新圖沒進到建置產物裡。

### 對外網址其實是登入頁，而且狀態碼是 200

**症狀**：用指令檢查網址回 200，判定站是通的。實際打開是部署平台的登入畫面，
外部的人根本看不到內容。

**原因**：新建的部署專案預設開啟存取保護，舊專案沒有這個預設，所以只有新站會中。
而登入頁本身是一個正常的頁面，回應狀態碼就是 200。

**做法**：兩件事一起做。①把新專案的存取保護關掉
②**驗收不能只看狀態碼，要看回應內容裡有沒有預期的文字**。
只驗狀態碼的檢查腳本會被登入頁騙過去。

## 五、驗收

### 只驗一頁，漏掉最顯眼的地方

**症狀**：商品列表頁驗得很仔細，結果被抓到的問題出在首頁的主視覺。

**原因**：驗收範圍憑印象決定，通常會挑「最容易出事的那頁」，反而漏掉「最常被看到的那頁」。

**做法**：整站走一遍才算驗過，順序固定：
首頁主視覺與各區塊圖 → 商品列表 → 商品內頁 → 購物車（加入並重新整理）→ 結帳 → 常見問題 → 行動版 390 寬。
完整清單見 `../quality/`。

### 自動驗收器的假陰性

**症狀**：驗收工具回報商品連結抓不到、加入購物車的按鈕抓不到，判定 FAIL，
但人工操作完全正常。

**原因**：兩種情況會誤判。①商品卡片用程式導航而不是 `<a href>`，選擇器抓不到連結
②按鈕文案被品牌客製過（例如「DEPLOY TO KIT」而不是「Add to Cart」），關鍵字比對抓不到。

**做法**：把這兩項標記成盡力而為的檢查項，FAIL 時**用截圖與實際操作複核，不要直接判定站壞掉**。
反過來也一樣：這兩項 PASS 不代表流程真的能走完。

### 用命令列正則檢查語言殘留，會拿到假的零命中

**症狀**：用中日韓文字的 Unicode 範圍去掃殘留文字，回報零命中，實際開站滿滿都是。

**原因**：部分平台的命令列工具對 Unicode 範圍語法的支援不一致，比對不到但也不報錯，
直接回傳零結果。這是最危險的一種失敗，因為它長得跟「通過」一模一樣。

**做法**：改用程式讀檔判斷字元範圍，或直接用瀏覽器看渲染結果。
更通用的一條原則：**任何檢查工具第一次回報零命中時，先造一個「應該要被抓到」的樣本餵給它，
確認它真的抓得到，再相信它的零**。

### 加權分數把違規蓋過去

**症狀**：品質檢查跑出 87 分，判定通過，交付出去之後才發現裡面有法規違規項。

**原因**：所有檢查項都被折算成分數再加總，違規項只是扣了幾分，總分依然過門檻。
實際發生過的版本是 `return score >= 75`。

**做法**：分數留著，但**分數不能是唯一的判定**。八層一起計分照舊，
**法規與正確性類另外標記為攔截項（blocking）：只要它沒過就一律判定失敗並以非零狀態碼結束，總分再高也不得交付**。
獨立的是「擋交付」這個判定，不是「計分」。這條是這條產線上單一影響最大的修正。

### 誤報變多時，把掃描範圍縮小

**症狀**：掃描器誤報率高到沒人想看，於是把掃描範圍縮小、把規則放寬，誤報是降了，
真違規也一起漏掉。

**原因**：誤報高通常有一個共同成因，縮範圍只是把症狀藏起來。

**做法**：**先找誤報的共同成因，不要縮範圍**。
實測數字：一次全專案掃描得到 26 個命中、其中 16 個是真違規，誤報率 38.5%；
把誤報逐一看過之後發現十條全是同一個原因（`salePrice || price` 這種取有效售價的寫法，
畫面上只有一個價格、沒有比較，本來就合法）。
排除這個慣用寫法之後，誤報降到 0，16 條真違規一條沒漏。
誤報率要用量的，不是用猜的，量完把數字與取捨理由寫進腳本註解留給後人。

### 產出的人自己驗自己

**症狀**：交付前的檢查全部 PASS，交出去被對方一眼看出問題。

**原因**：做的人與驗的人是同一個，知道哪裡薄弱就會不自覺避開那裡。

**做法**：驗收要由**沒有參與產出的人或流程**拿清單逐項跑，回報格式固定為逐項 PASS/FAIL，
每個 FAIL 附具體位置與證據（哪一頁、哪個商品、什麼狀態碼）。
禁止只回「看起來沒問題」，沒測到的項目要明說沒測。

## 六、後端服務層

> 前面幾章講的是「站長得對不對」，這一章講的是「站接不接得到真的商店」。
> 這兩件事會分開壞，而且接後端這件事壞掉的時候，畫面通常看起來完全正常。

### 前端帶著店主金鑰，等於把整間店的鑰匙公開發佈

**症狀**：站看起來一切正常，商品也讀得到。但把建置後的 `dist/assets/index-*.js` 打開搜尋
`consumer_key`，會發現商店的 Consumer Key 與 Secret 就寫在裡面。任何訪客按檢視原始碼都拿得到。

**原因**：規格書先前把金鑰放在 `VITE_WC_CONSUMER_KEY` 與 `VITE_WC_CONSUMER_SECRET`。
凡是 `VITE_` 開頭的變數，建置工具都會**編譯進瀏覽器的程式碼**，這是它的設計，不是設定錯誤。
實測驗證過：把 `VITE_WOO_URL` 設成某個網址後建置，該網址原封不動出現在 `dist` 的 js 檔裡。

會走到這一步的根本原因是**端點挑錯了**。商品查詢原本走 `wc/v3/products`，那條路一定要認證，
不給金鑰就是 401；為了讓畫面出得來，就只好把金鑰塞進前端。端點挑對就完全不需要金鑰。

這組金鑰是讀寫全權：拿到的人可以改商品價格、讀全部訂單、看客戶姓名地址電話。

**做法**：
- 公開展示（商品、分類）走 `wc/store/v1`，**不需要任何認證**
- 購物車與結帳走 `wc/store/v1`，用 Nonce 加 Cart-Token
- 會員查自己的訂單走 `wc/v3/orders?customer=me`，用**使用者自己的** JWT
- 需要店主權限的操作（批量上架、改商品）**只能在伺服器端腳本執行**，金鑰永遠不進前端
- 交付前一定要搜一次建置產物：`grep -rE "ck_|cs_|consumer_key" dist/`，**必須是零命中**

規格書已修正，見 `references/service-layer-spec.md` 最上方的 CAUTION 區塊。

### 接後端失敗會安靜退回假資料，畫面看不出來

**症狀**：站接上後端之後，商品照常顯示、價格照常、圖片照常。但後台改了商品，前台完全沒反應。
實際上前台從頭到尾都在用寫死在程式碼裡的示範商品。

**原因**：讀取失敗時的處理是「catch 住錯誤，改用示範資料」。這個 fallback 本身是對的，
它讓沒有後端的展示站也能跑。問題是**它沒有任何地方會叫**：沒有紅字、沒有警告、
主控台那行 warning 沒人會去看。於是「後端根本沒接通」和「後端接通了」在畫面上長得一模一樣。

搭配上一條就會變成：端點挑錯導致 401，401 被 catch 住，靜默退回假資料，
然後所有人都以為站接好了。

**做法**：
- 交付前用瀏覽器實際開頁面，打開網路面板確認**真的有一個 200 的 `wc/store/v1/products` 請求**
- 或用更硬的做法：在後台新增一個示範資料裡不存在的商品，看它有沒有出現在前台。
  沒出現就是沒接通，這個測法騙不了人
- 不要只看畫面有商品就當作接通了

### 只驗了假資料模式，就宣稱服務層做完了

**症狀**：後端服務層那一段（對應 `SKILL.md` 的 Phase 5）的驗收腳本全綠，交付了，實際接後端才發現讀不到商品。

**原因**：`scripts/validate_mock_flow.py` 的名字已經講明了，它驗的是 **Mock 模式**。
它檢查的是「程式碼裡有沒有出現 `isMockMode`、`VITE_WOO_URL` 這些字串」，
以及假資料模式下的流程跑不跑得動。**它從頭到尾沒有對真的後端發過一個請求。**
所以連線根本壞掉的站也能全綠通過。

**做法**：已經補上一支專門驗這件事的腳本：

```bash
python scripts/validate_live_flow.py <project_path> --site-url <站台網址>
```

它做兩件事：掃 `dist/` 確認金鑰沒有被編譯進去；把後端某個商品改名成一組隨機碼，
確認那組碼真的出現在畫面上，再改回原名並確認它消失。
改名成功而畫面沒出現，就是沒接通，這個測法騙不了。

兩個檢查都自帶偵測能力測試：先種出應該被抓到的樣本，抓不到就中止並宣告結果不算數。
後端可以用一行指令起起來，見 `docs/backend-poc.md`。
驗收清單的 A2 區段已經把這兩項列成必過關卡。

### 三個地方各自定義同一件事，而且互相矛盾

**症狀**：兩個站用 `VITE_WOO_URL`，規格書寫 `VITE_WC_API_URL`，驗收腳本檢查的是 `VITE_WOO_URL`。
生成新站的時候，模型跟著哪一份走就變成哪一種，每次都可能不一樣。

**原因**：服務層的程式碼**沒有樣板**。`scripts/inject_services.py` 只負責建資料夾和印出清單，
真正的程式碼是模型讀規格書當場寫出來的。散文寫的規格加上多份互相矛盾的來源，
產出自然會漂移。實際結果是三個範例站三種結構：一個站有一支服務檔、一個站兩支、
規格書說應該有六支。

**做法**：
- 環境變數名稱已統一成 `VITE_WOO_URL`，**空白代表假資料模式**，三份來源已經對齊
- 之後要改服務層的約定，三個地方要一起改：規格書、`inject_services.py`、`validate_mock_flow.py`
- 更根本的解法是把服務層抽成真的檔案樣板讓腳本複製，而不是每次請模型重寫一遍。
  這件事還沒做

### 純展示站沒接後端不是缺陷，但要講清楚是哪一種

**症狀**：拿到一個生成好的站，不知道它到底能不能接後端。翻程式碼才發現讀取函式是空的，
只留了一句「之後再接」的註解然後回傳空清單。照現況接後端，前台會一個商品都沒有。

**原因**：這其實是**設計上就允許的**。後端服務層注入是獨立的一段，而且明寫「用戶確認後」才執行。
沒跑那一段的站就是純前端展示站，商品寫在程式碼裡，這是合法的產出模式，不是壞掉。
問題只在於**站本身沒有任何地方標示自己是哪一種**，要翻原始碼才知道。

**做法**：
- 交付純展示站時，在該站的說明文件裡明講「純前端、商品寫在程式碼裡、不需要後端」
- 交付可接後端的站時，明講它需要什麼、怎麼指過去
- 判斷一個既有的站屬於哪一種，最快的方法是看 `src/services/api.ts` 有沒有讀 `VITE_WOO_URL`，
  以及那個分支底下是真的有實作還是回傳空陣列

## 七、產線本身的維護

### 產線有多份副本，從舊的那份同步會蓋掉新版

**症狀**：明明改好的規則不見了，回頭一看檔案退回到幾週前的版本。

**原因**：同一條產線同時存在多個位置（實際執行的那份、版控的那份、其他工具用的那份）。
同步腳本的行為是**先刪除目標目錄再複製**，等於鏡像。
從一份比較舊的來源跑同步，就會把比較新的目標刪掉。

**做法**：三件事。
①明確指定哪一份是正本，寫在文件裡，改動只改正本
②同步腳本要在執行前比對版本，偵測到來源比目標舊就中止，要覆蓋得明確加上強制參數
③同步前自動備份目標到隔壁的時間戳目錄。
另外要注意同步腳本實際同步了哪些位置，文件寫「全部同步」而實際上少同步一個位置，
會造成長期的版本分歧。

### 外部服務壞掉時安靜退回退路，然後回報成功

**症狀**：流程跑完、回報「完成」，但產出的東西明顯不對。
商品圖變成極簡線稿而不是商品照；或商品資料看起來正常，其實是內建的假資料，
根本沒有連上後端。**畫面不會報錯，所以沒有人發現。**

**原因**：外部服務失敗（金鑰失效、額度用完、端點改了）時，程式碼把錯誤接住，
改用退路繼續跑。退路本身是對的設計，**錯的是它沒有留下任何痕跡**。
失敗被吞掉之後，下游看到的是一個「成功」的結果。

實際發生過兩次，同一天，兩個不同的子系統：
生圖服務回 401 之後退回最陽春的線稿；
商店後端查詢回 401 之後退回內建假商品。

**做法**：

1. **退路可以走，但走了一定要說。** 最終報告裡必須有一行：
   「這一項用的是退路，原因是 X」。**不准安靜退回去。**
2. **驗證要驗結果，不是驗有沒有報錯。** 「沒有拋出例外」不等於「做對了」。
   要問的是「畫面上這批商品，是不是真的來自我以為的來源」。
   做法：先在來源端改一個只有真資料才會有的值，再確認它出現在畫面上。
3. **定期健檢外部服務的認證狀態。** 注意公開端點回 200 不代表金鑰有效，
   要打**需要認證**的端點才算數。
4. **退路的產出品質要撐得住。** 如果退路產出的東西一看就是半成品，
   那它不是退路，是一個延後爆炸的失敗。

### 用回應碼驗網站，會漏掉「頁面打得開但畫面是空的」

**症狀**：逐頁 curl 全部回 200，回報「全部正常」，
但使用者實際打開看到空白頁，或點導覽列沒有反應。

**原因**：單頁應用加上 rewrite 規則之後，**每一個網址都會回 200 並送出同一份 index.html**。
回應碼只證明伺服器有回東西，不證明前端程式跑起來、路由對得上、畫面畫得出來。
**200 是元件活著，不是結果發生。**

**做法**：

1. **用真的瀏覽器載入，讀畫面上的文字長度。** 少於幾百個字就是空的。
2. **要模擬點擊導覽列，不是只打網址。** 直接打網址走的是伺服器路由，
   點連結走的是前端路由，**兩條路徑不一樣，可能只壞一邊**。
3. **手機尺寸要另外測一次。**
4. **同時收集瀏覽器主控台的錯誤**，畫面空白通常伴隨一個 JavaScript 例外。

📌 順帶一個真的踩過的坑：**修好之後使用者可能還是打不開，因為他的瀏覽器把壞掉時的 404 存起來了。**
給他一個帶查詢參數的網址（例如 `?v=2`）可以繞過快取，一秒分辨「真的還壞」和「只是快取」。

### 自訂字體沒載入，站就退回系統預設，看起來像半成品

**症狀**：站做完了、版面沒破、顏色也對，但整體就是沒有個性，像未完成的樣板。

**原因**：設計選定的字體沒有真的被載入，瀏覽器退回作業系統預設
（`-apple-system`、`Segoe UI`、`Roboto` 這一類）。
**版面不會壞，所以任何檢查版面的驗收都抓不到。**

實際案例：同一天產出的兩個站，一個編譯後的樣式表裡是設計選的字體，
另一個是系統預設字體。後者看起來明顯比較差，但當下判斷成「風格問題」，
其實是字體根本沒進去。

**字體是識別的第一層。** 用系統預設等於沒有識別。

**做法**：

1. ⚠️ **用瀏覽器讀 computed style，不可以 grep 編譯後的 CSS。**
   同一個選擇器可能被宣告多次，**後者勝**，grep 第一個命中不等於生效值。
   2026-08-04 實例：系統字體堆疊在 byte 144045、站自己的字體在 byte 711904，
   **實際生效的是後者**，而 grep 抓到前面那個導致誤判成缺陷。
   出現 `-apple-system`、`Segoe UI`、`Roboto`、`system-ui` 當主字體就是 FAIL。
2. 確認字體來源真的有被引用（網頁字體的連結或 `@font-face` 宣告）。
3. 用瀏覽器實際載入後量 `document.fonts.check()`，確認字體真的可用而不只是宣告了。
4. **這一項要進交付驗收，不能靠肉眼。** 系統預設字體長得不難看，
   只是沒有個性，看習慣了不會覺得有問題。

📌 **2026-08-04 查明的根因：框架自帶的字體層會蓋掉設計字體（Radix Themes 案例）。**
同一天同一條產線的兩個站一對一錯，差別只有一個：UI 框架。

- 用 shadcn 或純 Tailwind 的站沒有框架字體層，`body` 上的設計字體直接繼承全站，怎麼做都對。
- 用 Radix Themes 的站，`@radix-ui/themes/styles.css` 自帶
  `.radix-themes { --default-font-family: -apple-system, BlinkMacSystemFont, ... }` 系統字體堆疊，
  而且 `<Theme>` 包裹元素會在自己身上設 `font-family: var(--default-font-family)`，
  **把 `body` 的字體繼承整條切斷**。只設 `body { font-family }` 在 Radix Themes 底下完全沒用，
  站內每一段文字都在 `<Theme>` 裡面，body 上那個設計字體會渲染在零個元素上。

**用任何自帶 theme token 的框架（Radix Themes 之類）時必須做兩件事：**

1. 在 `.radix-themes` 作用域覆寫 `--default-font-family` 與 `--heading-font-family` 成設計字體，
   不能只設 `body`。
2. 覆寫規則必須出現在框架樣式**之後**（selector 同為 `.radix-themes`，同權重靠順序決勝負）。
   把 `@import '@radix-ui/themes/styles.css'` 放在自家 CSS 檔最上方即可保證，
   但若框架樣式改成獨立 `<link>` 排在自家樣式之後，覆寫就會整個失效退回系統字體。

**驗收上另外兩個陷阱：**

- 靜態 grep 編譯後 CSS 的「第一個 `font-family`」會誤判：Radix 的系統堆疊 token
  永遠排在檔案前段，就算覆寫成功也照樣 grep 得到它。正確判準是瀏覽器的 computed style：
  掃所有帶文字的元素讀 `getComputedStyle(el).fontFamily`，並列出 `document.fonts` 裡
  status 為 loaded 的字體，兩邊都要對上設計字體。
- **設計了三個字體，可能只有兩個真的在畫面上。** 被切斷繼承的那個不會報錯、不會破版，
  就是安靜消失。驗收要確認每一個設計字體都渲染在至少一批元素上，
  Google Fonts 只載入有被用到的字型檔，所以「宣告了卻沒 loaded」本身就是訊號。
