# 展示介面

**狀態：規劃中，尚未開始實作。**
這份文件說明它要解決什麼問題、預計長什麼樣、為什麼還沒動工，以及在它做出來之前，不看程式碼的人現在該從哪裡看起。

---

## 為什麼需要它

這個 repo 目前所有的入口都是文件與原始碼。想知道這套系統做得到什麼，動線是「讀 README → 讀部門說明 → 讀生產線規範 → 想在瀏覽器裡實際點一點，還得自己起一個本機伺服器」。

那是給工程師走的動線。不寫程式的人被迫走同一條，第一個看到的畫面是一份技術文件，不是一間店。

這個介面要補上另一半：一個網頁，不需要閱讀文件、不需要安裝、不需要執行任何指令，就能看到這套系統的各部門能力與實際產出。

## 在它做出來之前，請走這條

1. **看實際畫面與可以點開的網站** → 根目錄的 [`README.md`](../README.md)。最上面就是三個站的首頁截圖，以及線上運作中的網站連結，直接點開即可，不必安裝任何東西。
2. **想多看幾張畫面** → [`examples/screenshots/`](../examples/screenshots/)，每個站有首頁、商品頁、手機版。
3. **想知道一個站是怎麼被做出來的** → [`docs/how-it-works.md`](../docs/how-it-works.md)，有一張從輸入到上線的流程圖。

這條路現在可以用，但它是拼湊出來的：你得先知道要點哪幾個檔案。這個介面要取代的正是這件事。

## 這個介面預計長什麼樣

### 會呈現什麼

**部門總覽**
13 個部門的現況一目了然，哪些在運作、哪些規劃中，各自負責什麼。

**每個部門的實際產出**
點進部門，看到它做過的事。不是描述，是可以點開的東西。

**產出可以直接點開**
點一個網站，直接看到那個店面長什麼樣，不需要安裝或執行任何東西。

**能力與規模**
累積產出的網站數量、設計規範的涵蓋範圍、生產線的品質關卡。

### 刻意不呈現什麼

**不做即時狀態。** 這個介面不顯示現在有誰在執行什麼、執行了多久、進度百分之幾。

理由：**這是一個成果展示，不是監控面板。** 這套系統的價值在於它累積出什麼，不在於它此刻在忙什麼。即時狀態對看的人沒有決策價值，只會製造被監看的感受。

### 技術方向

靜態頁面，資料從本 repo 的內容生成，不另外維護一份。

**這樣做的原因**：如果介面與 repo 各自維護一份內容，兩邊必然在幾週內不一致，那比沒有這個介面更糟。單一來源可以確保打開介面看到的就是 repo 裡的事實。

行動裝置優先，因為多數人第一次打開它會是在手機上。

## 為什麼還沒做

三個原因，照重要性排：

1. **它要顯示的內容本身還在動。** 這個介面的資料要從 repo 的內容生成（見上面的技術方向）。而 repo 這段期間仍在修部門說明、產線規範與驗收口徑，現在做出來的介面，內容過幾天就得跟著重做一次。
2. **它是加分項，不是必要項。** 目前排在前面的是產線本身的缺陷：視覺重複、驗收漏檢這一類，那些直接決定交出去的網站品質（見 [`production-line/VERSION_HISTORY.md`](../production-line/VERSION_HISTORY.md) v11.1）。展示介面不影響任何一個站的品質。
3. **它的資料來源還沒收斂。** 「累積產出的網站數量」「部門現況」這些數字目前散在不同檔案裡各自手動維護。要先讓這些事實有單一來源，這個介面才不會變成又一個需要人工同步的地方。

**沒有排定時程。**
這份文件不承諾它何時會做，也不承諾它一定會做。上面第 2 點成立的期間，它就不會被排進去。狀態有變，改這份文件。
