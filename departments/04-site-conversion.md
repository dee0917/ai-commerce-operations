# 04 建站與轉換

**現況：運作中，產出量最大的部門**

## 職責

兩件互相銜接的事。第一，把一個商品或一個構想做成看起來像正規公司做的、可以真的下單的電商網站。第二，持續優化它，讓進來的人更多變成訂單。

一條龍由同一個部門負責到底，才不會出現「網站做得漂亮但沒人買」或「轉換建議跟網站實際做法對不上」。

## 實際產出

**35 個站在線上運作。** 33 個是 2026-08-03 以前的存量，另 2 個是 2026-08-04 最新一輪的產出。2026-08-05 逐一以 HTTP 實測，35 個全部回應 200。本機保有原始碼的 23 個，其中 20 個已編譯。

**單站 29 分鐘。** 兩個全新的站各自實測，30.1 與 28.2 分鐘，差距 6%。兩個站是平行跑的，所以這是各自的實際耗時，不是兩站相加。同一天內完成過 6 個站（以各站的建置紀錄確認）。

**每站 15 個路由**，含商品列表、商品詳情、購物車、三步結帳、常見問題、法務頁。

**三個完整範例站進 repo**，原始碼與編譯版都在，不需要金鑰、不需要付費服務、不需要資料庫就能跑起來：

```bash
cd examples/vanguard/dist && python -m http.server 8000
```

**後端走完一次完整買賣。** 在管理後台手動新增一個商品，前台立刻看得到；加入購物車、填地址、送出訂單；後台出現這筆訂單，庫存自動從 15 變成 14。訂單明細裡系統自己寫下的紀錄是 `Stock levels reduced: (15→14)`。全程 16 張截圖在 [`docs/backend-screenshots/`](../docs/backend-screenshots/)，完整紀錄在 [`docs/backend-poc.md`](../docs/backend-poc.md)。

**一次上架 412 個品項，0 個失敗。** 上架前資料庫 13 筆，上架後 425 筆，移除那批之後回到 13 筆，三個數字都直接查資料庫確認過，不是從畫面推算的。同一批商品跑第二次是更新 412 筆、新增 0 筆，總數不變。這是拿整個商品池當壓力測試跑的，不是一個站真的要放 412 個商品：正常一個站只承接池子裡的一個分類。

## 現在卡在哪

**三個範例站裡只有一個真的接過後端。** 第二個結構幾乎相同、判斷可以套同一份修正，但沒有實際接過。第三個接不上：它的商品欄位定義是另一套，商品編號是文字不是數字，而且後端讀取函式裡面根本沒有實作，只留了一句註解然後回傳空清單。照現況接上去，前台會一個商品都沒有。

**沒有真金流。** 付款走的是自己寫的模擬外掛，按下確認就直接標記成已付款，不聯絡任何金流公司。設計上換成真外掛前端不用改，因為前端是去問後端有哪些付款方式可用，但這一點沒有實際驗證過，不能當成已確認的事。

**轉換這半邊一個真實數字都沒有。** 站沒開賣，跳出率、加購率、棄單率、回購率全部是空的。目前所有轉換相關的做法都停在規範層面，沒有經過真實流量檢驗。

**還有幾件明確沒做**，分別記在 `docs/backend-poc.md` 的兩處。「沒有做到的，誠實列出」那一節：沒有會員登入註冊（目前是訪客結帳）、沒有退貨退款與出貨、沒有壓力測試（412 個商品成功，沒測過更大的量，也沒測過多人同時下單）。「目前的限制」那張表：寄不出訂單確認信、沒有加密連線、前台還是開發模式沒打包。
