# 電商站交付驗收清單（檢查 agent 跑）

> 核心原則兩條：**產出與檢查必須分開**，以及**驗收本身要能被檢查**。
>
> **用法**：一個站被「產出與修復的角色」做完後，交給**獨立的驗收角色**
> （必須與產出者不是同一個，避免球員兼裁判）跑此清單，回傳逐項 PASS/FAIL 表。
> A 層全數 PASS 之後，由人看截圖做最終拍板。
>
> 分兩層：**A 是客觀的是非題**（機器可驗，直接判）；
> **B 是品味評分**（先評分，最後由人簽核）。

---

## A. 客觀 yes/no 閘門（任一 NO = 未過，不得交付）
用 Playwright 開站，截四張：首頁、商品詳情、結帳、行動版（<768px）。逐項判 PASS/FAIL。

1. 首頁、/shop、商品詳情、結帳 每一頁都正常渲染（非空白、非 404）？
2. 全站 0 破圖（每張 img.naturalWidth>0、無 network 回應 >=400）？
3. 每個商品圖都對得上該商品（沒有離題／放錯，例：頌缽站不能出現啞鈴照）？
4. 每個商品只留一張對版主圖、圖沒有重複佔位（images[1] 不是死圖 placeholder）？
5. 加購 → 改數量 → 走到結帳看得到明細＋金額，且重整後購物車還在（persist）？
6. 換頁自動回頂（ScrollToTop 有掛）？
7. 主要 CTA、價格、庫存狀態一眼可見，首頁到結帳 ≤ 3 次點擊？
8. 行動版 <768px 不破版、圖不變形、無元素互相重疊（標籤/浮動 icon/描述文字）？
9. deep route（/shop、商品頁）直接開或重整不 404（public + dist 都有 vercel.json SPA rewrite）？
10. 導覽列、footer 連結、按鈕都點得動、無死連結、主控台無 error？
11. **驗收本身有沒有偵測能力？** 跑完上面十項之後，故意製造一個已知的錯誤（例如把一張商品圖改成不存在的路徑、或把一個連結改成死連結），確認上面的檢查真的會抓到。**抓不到就代表這份清單對這個站沒有偵測能力，全 PASS 不算數。** 驗完要把改動還原。

11.5 **有沒有東西是安靜退回退路產出的？** 檢查這一輪有沒有任何外部服務失敗
    （生圖、商品資料、後端查詢）。**失敗而沒有在報告裡寫出來，這一項就是 FAIL。**
    退路可以走，但走了一定要說。畫面看起來正常不算數，要確認資料真的來自它該來的地方。
    📌 2026-08-04 同一天撞到兩次：生圖服務失效退回極簡線稿、後端查詢被擋退回假商品，
    **兩次都回報成功，兩次都沒人發現。**

11.6 **做出來的東西有沒有照它自己選的 DNA 做？** 由**驗收角色**跑，不是產出者自己跑：

```bash
python production-line/scripts/check_dna_fidelity.py <project_path>
```

腳本三邊對照：**編譯後 CSS 的實際底色與字體 ↔ `data/design-history.json` 登記的主 DNA ↔ `references/real-ecommerce-dna.md` 那個 DNA 條目的規格**。
底色與主要字體只要有一項無法從選定的 DNA 條目引出來，就印出「規格說 X、實際是 Y」並判 **FAIL，不得交付**，要回設計階段重做（**不可以改 DNA 編號來遷就已經做出來的結果**）。
讀不到底色、認不出字體類別、DNA 條目本身寫不清楚，一律算 FAIL：判不出來與做錯了，對交付的意義完全一樣。
跟第 11 項同一個原則，腳本會先造出故意違反 DNA 的假樣本自我測試，不通過就中止並宣告結果不算數。
📌 2026-08-04 實證：某站選了 DNA-44（條目寫「White/light neutral base」＋「Bold sans headings」），
交出的是暖紙底 #f5f3ee ＋襯線標題。**版面沒壞、字體有載入、當時每一項驗收都是綠的**，
因為在這一項之前，沒有任何一關看的是「有沒有照選定的 DNA 做」。
📌 字級階層、展示字型配額、eyebrow、留白節奏、圓角與圖比屬於
`references/typography-baseline.md` 的鎖值，用 Playwright 讀計算後樣式驗，不在這一項裡重複定義。

11.7 **畫面上「看得見」的東西夠不夠？** 不可以用「網頁裡有沒有文字」判定。
    `innerText` 會把 `opacity:0`、還沒進場的元素也算進去，**看起來有 4000 字，實際是一片空白。**
    要量的是每個元素的 **computed opacity 與 visibility**，並確認首屏可見元素數量合理。
    工具：`production-line/scripts/check_visible.mjs`（全站爬用 `crawl_all.mjs`）。
    📌 2026-08-04 就是這樣誤判：腳本說 4385 字正常，使用者截圖整片空白。

11.8 **換一個沒開過的網址驗一次。** 部署過程中若曾經出現壞掉的版本，
    使用者的瀏覽器會把壞掉那版的骨架存起來，之後修好了他還是看到空白。
    **交付前用一個全新網址（或無痕視窗）確認一次**，那才是新使用者會看到的。
    📌 順帶：`vercel.json` 一定要設 HTML 不快取、只讓 `/assets/` 長快取，否則同樣的事會一再發生。

11.9 **自訂字體真的生效了嗎？** ⚠️ **必須用瀏覽器讀 computed style，不可以搜原始碼。**

    做法：用真的瀏覽器開站，對 h1 與 body 各讀一次 `getComputedStyle(el).fontFamily`，
    再跑 `document.fonts.check()` 確認字體真的可用而不只是宣告了。
    讀出來的主字體是 `-apple-system`、`Segoe UI`、`Roboto`、`system-ui` 才算 **FAIL**。

    ⚠️⚠️ **不可以用 grep 搜編譯後的 CSS 判定。**
    同一個選擇器可能被宣告多次（建置工具會合併多個來源），**後出現的勝**，
    搜到第一個命中不等於生效值。

    📌 2026-08-04 實例：某站樣式表裡同一個變數出現兩次，
    系統字體堆疊在 byte 144045、站自己的字體在 byte 711904，**實際生效的是後者**。
    當時用 grep 抓到前面那個，**誤判成「字體壞了」並寫成缺陷報告出去**。

    📌 **這一項不能靠肉眼。** 系統預設字體長得不難看，只是沒有個性，
    版面也不會壞，所以任何檢查版面的驗收都抓不到。

## A2. 接了後端的站，另外要過這兩關（純展示站只跑第 12 項）

由驗收角色執行，**不是產出者自己跑**：

```bash
python production-line/scripts/validate_live_flow.py <project_path> --site-url <站台網址>
```

12. **建置產物裡沒有任何金鑰**（`ck_` `cs_` `consumer_key` `sk-` `ghp_` `AKIA` 私鑰區塊）？
    凡是 `VITE_` 開頭的變數都會被編譯進瀏覽器程式碼，任何訪客看得到。
    有命中就是 FAIL，而且是**不得交付**等級，不是扣分而已。
13. **畫面上的商品真的來自後端**？腳本會在後端把某個商品改名成一組隨機碼，
    確認畫面上出現那組碼，再改回原名並確認它消失。
    只看「頁面有商品、沒報錯」不算數：讀取失敗時前端會靜默退回寫死的假資料，畫面看起來完全正常。
    純展示站不適用這項，改用 `--secrets-only`，但要在交付說明裡明講它是純展示站。

這兩項跟第 11 項同一個原則：**先證明檢查工具會叫，再相信它說沒事**。
腳本自己會先種出應該被抓到的樣本做自我測試，不通過就中止並宣告結果不算數。

## B. 品味 rubric（照《好電商站 Rubric v1》，agent 先評、我簽核）
完整定義在 [`./site-rubric.md`](./site-rubric.md)，**不在這裡重寫**（單一真相）。門檻：
- 原創性、設計品質、品牌文案 三個權重維度 各 ≥ 4/5；
- 商業真實感、技術執行、可用性 各 ≥ 3/5；
- Rubric 的禁令清單一條都不能出現（AI 字體、漸層裁字、blob 光暈、破折號黏句、「不是 A 而是 B」、假評論…）。
- ⚠️ 自動化的品味評分只當**初評參考**；最終「這站夠不夠成熟、能不能交付」由人看桌機與手機截圖拍板。這一步不外包，關鍵節點保留人工判斷。

## 回報格式（給檢查 agent）
- 逐項列 PASS / FAIL，每個 FAIL 附**具體位置＋證據**（哪一頁哪個商品、截圖路徑、破圖 URL、network 狀態碼）。
- B 層附各維度分數＋扣分原因。
- 禁止只回「看起來 OK / 應該沒問題」。沒測到的項目要明說沒測。
- 結論：READY-FOR-TASTE（A 全過，待我簽核）或 NOT-READY（列出擋住的項）。

## 工具備忘（跟現有腳本對齊，別重造）

**以下每一支都在本 repo 的 `production-line/scripts/` 裡，指令可以照抄直接跑。**
沒列在這裡的工具就是本 repo 沒有，要用之前先確認它存在，不要照著舊備忘找不存在的檔。

| 要驗什麼 | 指令 | 這支到底做什麼 |
|---|---|---|
| 靜態八層總檢（對應本清單第 1、2、9、10 項的一部分） | `python production-line/scripts/ecommerce-checklist.py <站目錄>` | 掃原始碼與 `dist/`：建置、路由掛載、電商邏輯、圖片健康度、SEO、反面樣式、安全、UK/EU 合規，逐層印計分卡。全過回傳碼 0，有一層沒過回傳 1。**這支不開瀏覽器，過了不等於畫得出來。** |
| 畫面上看得見的東西夠不夠（第 11.7 項） | `node production-line/scripts/check_visible.mjs <網址> <路由1> <路由2> ...` | 開真的瀏覽器，逐個元素讀 computed opacity 與 visibility，只算真的看得見的。用來擋「`innerText` 有 4000 字、畫面卻整片空白」。 |
| 全站每一頁都不是空的 | `node production-line/scripts/crawl_all.mjs <網址>` | 從首頁爬出所有站內連結，逐一開起來看畫面內容。只信畫面，不信回應碼。 |
| 有沒有照選定的 DNA 做（第 11.6 項） | `python production-line/scripts/check_dna_fidelity.py <站目錄>` | 編譯後 CSS 的底色與字體 ↔ `data/design-history.json` 登記的 DNA ↔ `references/real-ecommerce-dna.md` 的規格，三邊對照。自帶變異測試，抓不到假樣本就中止。 |
| 假資料模式的服務層完整性 | `python production-line/scripts/validate_mock_flow.py <站目錄>` | 驗商品、購物車、登入、訂單、結帳在 Mock 模式下全部走得完，含 `.env.example` 與建置。**注意：這支從頭到尾沒對真後端發過請求**，全綠不代表接得通。 |
| 真連線與金鑰外洩（第 13 項） | `python production-line/scripts/validate_live_flow.py <站目錄> --site-url <網址>`<br>純展示站用 `--secrets-only` | 一：掃 `dist/` 全部檔案找被編譯進去的 `VITE_` 金鑰。二：在後端把某商品改名成隨機碼，確認畫面上真的出現那組碼再改回去。兩個檢查都自帶偵測能力測試。 |
| 建置壞掉時自動修 | `python production-line/scripts/auto_fix_build.py <站目錄>` | 反覆跑 `npm run build`（最多 5 輪），解析 TypeScript 編譯錯誤並套已知修法。**這是產出端的工具，不是驗收工具**，驗收角色不該用它把 FAIL 修掉再宣稱通過。 |

**環境前提**：`check_visible.mjs` 與 `crawl_all.mjs` 需要 Playwright。
這兩支住的資料夾沒有 `node_modules`，要嘛在裝了 Playwright 的專案裡跑，
要嘛把全域 `node_modules` 路徑放進 `NODE_PATH` 再跑。**路徑依環境而定，本 repo 不寫死。**
