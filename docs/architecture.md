# 架構

## 三層結構

```
┌─────────────────────────────────────────────┐
│  營運層                                      │
│  13 個部門，各自負責一段職能                  │
│  策略 / 研究 / 創意 / 建站 / 流量 / 數據 / 研發 │
└──────────────────┬──────────────────────────┘
                   │ 需求與規格
                   ↓
┌─────────────────────────────────────────────┐
│  生產層                                      │
│  電商網站生產線                              │
│  設計規範 21 份 · 自動化腳本 17 支            │
└──────────────────┬──────────────────────────┘
                   │ 產出
                   ↓
┌─────────────────────────────────────────────┐
│  產出物                                      │
│  獨立的靜態電商前端                          │
│  與生產層解耦，可單獨部署與維護               │
└─────────────────────────────────────────────┘
```

## 三層各自的性質

### 營運層
純文字的職責定義。每個部門說明自己負責什麼、在什麼情況下被叫用、產出什麼。

**這一層是可讀可改的文件，不是程式。** 好處是任何人打開就看得懂這套系統怎麼分工，要調整分工只需要改文字。

### 生產層
設計規範（文字）＋ 自動化腳本（Python）。

**規範是平台無關的**：模板庫、品質標準、流程步驟、反面教材清單，這些是純文字資產，任何能讀檔的系統都能使用。

**執行層目前跑在 Claude Code 的 Agent Skills 上**，負責把規範轉成實際動作：讀規格、生成程式碼、跑檢查、修正。

### 產出物
標準的靜態前端專案，**與上面兩層完全解耦**。

React 19 + TypeScript + Vite + Tailwind CSS 3。產出後可以獨立開發、獨立部署、交給任何前端工程師接手，不需要這套系統也能運作。

## 為什麼要解耦

如果產出的網站綁在生產線上，那這套系統就變成一個必須一直存在的依賴。

解耦之後：
- 產出的站可以獨立交付給客戶或團隊
- 生產線改版不會影響已經產出的站
- 任何人拿到站的原始碼都能繼續開發

## 品質保證的位置

品質檢查刻意分成四個不同的位置，而不是集中在一處：

| 位置 | 檢查什麼 | 由誰做 |
|---|---|---|
| 生產層內建 | 結構性錯誤（破圖、缺價格、斷連結） | 生產線自己 |
| 交付前驗收 | 使用者實際會看到的畫面 | 獨立的驗收角色 |
| 合規閘門 | 法規違規一樣計分，但標記擋交付，違規一律擋下 | 13 法遵與風控 |
| 最終確認 | 成熟度與品味 | 人 |

**分開的理由**：每一層抓得到的問題類型不同。集中在一處的話，前面漏掉的後面沒有機會補。
